overview: discrete is a login item running in the background that acts as a quick access toolbox and command center. this version allows tool defined via files (open file, execute script, open apps) and builtin functions shipped with discrete (see builtin toolkit).
    discrete is background only: no window at launch and no dock icon. the display (overlay) is the only UI.

initialization
    run the following command to make the OS's caplock keytap duration to match with discrete such that the capslock key either toggle discrete or toggle capslock, never both or neither.
    hidutil property --set '{"CapsLockDelayOverride":${userSettings.TimeInterval in ms}}'

entry
    when i click capslock. the display pops up, discrete is now active!
    while inactive, pressing CapsLock down starts a short in-memory activation buffer. keys newly pressed after it (ordinary keys, modifiers, and mapped f/media keys) are recorded in key-down order even if they are released before CapsLock.
        on a CapsLock tap, enter state.root, then resolve the buffered key-downs oldest first as if released sequentially after activation. each key is delivered once to the mode/state left by the previous input; typing modes retain the original characters and modifier flags. stop replay if an action exits discrete or opens the file picker.
        eventual releases and auto-repeats of replayed keys are consumed until each key is physically released, so they cannot trigger twice or leak into another app after a command exits. keys already held before CapsLock aren't buffered.
        potential shortcut input is deferred during the tap decision so it doesn't reach the foreground app. if CapsLock becomes a hold (including while still held), discard the activation queue and pass its original events to that app in order. normal inactive typing otherwise passes through unchanged. the buffer is never saved to disk and is cleared after each activation or hold.

display
    the top line should be the state's name, exactly as the user typed it (no case change). a name can be empty, in which case the top line is blank.
    each line after is an action of the state, sorted by their key's assignment (key list order). this includes the system actions ("configure", "return to previous state", "search"): they are sorted together with the user defined actions, not appended at the end.
    the capslock row (not part of the orderable key list) is always the last row.
    the UI will display all these actions as a list, the input's symbol and then the text description of what the input does to the state: for instance, "[symbol representing trigger key] [trigger name]". an action with an empty name shows only its symbol.
    display is always on the screen with the user's mouse pointer (for multi window/screen situations). the screen is re-checked every time the display updates.
    display is horizontally centered with its top aligned to the top of the screen (just below the menu bar), so when its number of rows changes only its bottom edge moves.
    display always visible if and only discrete is active (this includes while the file picker is open, where the display shows that a file is being selected).
    a title, context, command/item name, or secondary detail that overflows its available width stays at its beginning for 1.2 seconds, then scrolls left at userSettings.overflowScrollRate (default 6 characters/second, using the text's average character width). two copies separated by a small gap make the loop seamless; it pauses at the beginning again after each full loop. text that fits stays still. changing the text, available width, font, or rate restarts the pause. a zero or negative rate disables scrolling and keeps normal truncation.

terminologies
    transition: movement of one state to the next
    function: tools that extends beyond the discrete app
    builtin function: a function shipped with discrete itself (instead of a user chosen file), taken from the builtin toolkit
    builtin toolkit: the fixed, read-only tree of builtin functions (grouped in builtin folders) that ships with discrete
    action: either a transition or a function. all action are called given a state
    input: a discrete key click or some physical input (used to trigger an action)

underlying mechanism
    the app manage a graph of nodes called states (how this is stored depends on implementation).
    each state have actions triggered by input
    each action can transition to a sub-state or call a function
    a function is its own kind of action, not a state: it has a name and a target, and no sub-states. the target is either a file (chosen with the system file picker) or a builtin function (chosen from the builtin toolkit).
        a builtin target is stored by a stable id of the builtin function, not by its name, so the user's name for the function is independent of the builtin's name.
    in this way, the user can create an arbitrarily large toolkit accessible with just a few clicks
    the system should keep track of key list, a list of the keys that physically exist on the connected keyboard(s) (see key_list)
    all the actions can be set to any input key (assuming no overlap). the key list is ordered, and that should be the displayed order of actions
    names (of states and functions) can be any text, including empty.

key_list
    the list of keys is in this order. discrete listen for physical key lifts (that aren't held keys, specified by key tap duration) there should be a different symbol for each key:
        command (left (default symbol) and right (R+default symbol), left precede right)
        option (left and right)
        control (left and right)
        shift (left and right)
        tab
        esc
        ` (backtick)
        f keys (f1, f2,... regardless if mac is in fn mode or not)
        delete
        enter
        arrow keys (ordered by keycode: left, right, down, up)
        all letters in the alphabet (no capitalization, shift + a is treated as shift clicked then a clicked, not one key called A),
        *any other keys, ordered by keycode
        capslock tap (no action can be bound by capslock, this is a reserved system key)

    symbols
        command ⌘ / R⌘, option ⌥ / R⌥, control ⌃ / R⌃, shift ⇧ / R⇧, tab ⇥, esc ⎋, backtick `, f keys F1 F2 ..., delete ⌫, enter ⏎, arrows ← → ↓ ↑, capslock ⇪
        letters and other keys show the character that key types in the current keyboard layout (e.g. on AZERTY the key in the QWERTY "a" position shows "q")

    key identity
        a key is identified by its physical key (hardware key code), not by the character it types. a binding stays on the same physical key when the keyboard layout changes.

    tap rule (applies to every trigger input, not to typing in state.text_string)
        a key counts as a tap if it is released within the tap duration (user setting, default 0.25s) of being pressed. the input fires on release. the activation buffer described under entry is the exception: its key-downs resolve immediately after CapsLock activates discrete.
        a key held longer than the tap duration is a hold and does nothing.
        taps that overlap fire in the order the keys were pressed: a key released early waits until every key pressed before it has been released (or has become a hold). e.g. a quick shift+a fires shift, then a.
        a modifier (command/option/control/shift) is an input by itself: tapping it alone is a tap of that key.

    while discrete is active, every key event (including modifier and f key/media events) is consumed by discrete and never reaches other apps.

    only keys available on the system are part of the key list: a key is in the list only if it physically exists on at least one connected keyboard. the order above is kept; missing keys are simply skipped (e.g. the built in macbook keyboard has no right control, so right control is not in the list and nothing is ever assigned to it).
        how availability is decided: keyboards do not reliably report which keys they physically have (the macbook keyboard claims to have right control), so each connected keyboard is matched to a known profile and the key list is the union of their keys:
            apple compact (built in laptop keyboards, magic keyboard): every modifier except right control, fn, esc, tab, `, f1-f12, delete, enter, arrows, letters, digits, punctuation, space. no keypad, no home/end/page up/page down/forward delete.
            apple with numeric keypad (magic keyboard with numeric keypad): apple compact + f13-f19 + home/end/page up/page down/forward delete/help + keypad.
            any other keyboard: a full standard keyboard (all modifiers including right control, no fn, f1-f12, home/end/page up/page down/forward delete/insert, keypad).
            plus the layout's extra keys (the extra key next to left shift on ISO, the extra keys on JIS).
            devices that only pretend to be keyboards (security keys, mice) are ignored. if no keyboard is recognized, a full standard keyboard is assumed.
        the key list is re-checked every time discrete is entered (tap capslock), so plugging in or removing a keyboard takes effect the next time discrete opens. system keys (configure, back, search, configuration options) are assigned from the current list, so they can move when the list changes.
        only keys in the key list can be chosen as a new trigger.
        a user action bound to a key that is no longer in the list (its keyboard was disconnected) is never deleted: it stays in the graph and is displayed dimmed and marked "(key not connected)" until the key is available again. it cannot be triggered meanwhile.

    reserved keys
        capslock: never bindable. in any state, a capslock tap leaves discrete (see os level transition map).
        esc: inside state.?.conf and all of its sub-states (and state.text_string, state.search, state.builtin_select and state.builtin_select.search), esc always means "exit"/"end config"/"cancel". since every screen that picks a trigger uses esc to exit, esc can never be bound as a trigger, and it is never assigned to configure, back, search, or a configuration option.

os level transition map
    regular computer use -- input: press other keys, use mouse, ect -> regular computer use
    regular computer use -- input: tap capslock -> state.root
    state.root.some_state -- input: tap capslock -> regular computer use
    any state inside discrete (including state.?.conf, its sub-states, state.text_string, state.file_select, state.builtin_select, state.builtin_select.search and state.search) -- input: tap capslock -> regular computer use
        if this happens in the middle of an edit, the edit is cancelled first, exactly as if esc was tapped (see "cancel" below), then discrete exits. nothing half finished is kept.

while the user is at an arbitrary state (named ?), theses are actions they can take (again, will be displayed)

state.?
    "unoccupied key" means a key in the key list (except capslock and esc) that no user defined action of state.? is bound to.

    state.? -- input: 1st unoccupied key. display: "configure" -> state.?.conf

    (if there is a previous state) state -- 2nd unoccupied key in key list. display: "return to previous state" -> return to previous state
        the previous state is the state's parent. the root has no previous state, so it has no back action.

    (root only) state.root -- 2nd unoccupied key in key list. display: "search" -> state.search
        the root uses the key that would be "return to previous state" for search instead.

    with no user bindings on them, configure is left command (⌘) and back (search at the root) is right command (R⌘). if the user binds a user action to one of these keys, configure/back/search move to the next unoccupied keys in that state.

    for as many user defined actions (either a function or a transition from state.?):
        state.? -- input: key the user defined "[key]{new state name}" -> go to state.?.next? if the action transitions to a new state or run the function if it is a function
        running a function: a file target is opened (app opened, executable script run, other file opened with its default app) and discrete exits. a builtin target does what that builtin does (see builtin toolkit) and then discrete exits, like a file target, unless the builtin's description says it stays active.
            .app resources and app search results use intelligent application opening (below). other resources keep their normal opening behavior.

    intelligent application opening
        "desktop" means a macOS Space, including a native full-screen Space; "monitor" means a physical display. the destination is the monitor and current desktop under the mouse when opening is requested.
        if app A is displayed on that desktop, opening A cycles through its windows in Mission Control desktop order, wrapping around. for A with one window on each of desktops 0, 1, 5, opening from 1 goes to 5, then to 0. other monitors are left alone. multiple displayed A windows on one desktop cycle focus in stable window-id order before advancing to the next desktop; changing focus within a desktop never switches desktops. with only one local desktop, focus wraps to its first window. an all-desktops window does not create extra desktop stops. opening from another app without a focused A window uses desktop order.
        with multiple monitors, if A is not displayed on the pointer's current desktop, bring its first window that isn't displayed on any monitor onto that desktop and monitor. minimized or hidden windows count as not displayed. an occluded window on a current desktop still counts as displayed.
            if all A windows are displayed already, bring the first one instead. windows are ordered by their Mission Control desktop order, with stable window ids breaking ties.
        with one monitor and no A on the current desktop, focus the first existing A window on its own desktop. if A has no windows, launch/reopen A and place its first window on the pointer's desktop and monitor.
        moving keeps the window's size and relative placement (shrunk to fit), preserves maximized placement, and leaves/re-enters native full screen as needed, as with move window to next monitor.
        this logic is separate from general resource opening and is also the "open application intelligently" builtin. it needs Accessibility permission and optional private macOS Spaces APIs. if Spaces information is unavailable, fall back to normal application opening. if movement is unavailable or rejected (including another app's native full-screen destination desktop), focus the existing window on its original desktop instead. no SIP changes or external window manager are needed.

    state.? -- input: capslock tap. display: "exit discrete" -> regular computer use

below defines configuration options for an arbitrary state (named ?, the root state is named "root" but can be renamed). state.?.conf means configuration of state named ?.
state.?.conf
    each of the configuration have input triggers of first, second, ... available key (all keys in the key list except capslock and esc), etc based on the order on this document.
    state.?.conf is its own state with no user bindings, so these keys do not depend on state.?'s bindings and are the same in every state. they depend only on which keys are available; with a full standard keyboard (right control present) they are:
        name this state        ⌘
        delete this state      R⌘  (at root this key is reserved but does nothing and is not displayed, so the keys below never shift)
        new state              ⌥
        add a function         R⌥
        delete a function      ⌃
        rename a function      R⌃
        set function trigger   ⇧
        update function        R⇧
        end config             ⎋
        on apple keyboards (no right control), everything after "delete a function" moves up one key: rename a function ⇧, set function trigger R⇧, update function ⇥.
        delete a function, rename a function, set function trigger and update function are only available when state.? has at least one function. otherwise their keys are reserved but do nothing and are not displayed (same as delete this state at root), so no key shifts.

    all sub-states of state.?.conf exit with esc ("exit"). exiting a sub-state goes to state.? unless stated otherwise.

    state.?.conf -- input: esc. "end config" -> transition: state.?

    state.?.conf -- "name this state" -> transition: state.text_string[
            save = state.?.name
            exit = (transition: state.?.conf)
            cancel = (transition: state.?.conf)
        ]

    state.?.conf -- "delete this state" -> (this is only available for the non-root state). state.?.conf.del_state
        state.?.conf.del_state -- display: "[R⌘] tap again to delete {state name} and {n} sub-states"
        state.?.conf.del_state -- input: the same key again -> delete the state and everything under it, and transition to the state's parent. (the parent state will also lose transition to this state).
        state.?.conf.del_state -- input: any other key (including esc) -> nothing is deleted. transition: state.?.conf

    state.?.conf -- "new state" -> state.?.conf.add_state
    state.?.conf.add_state -- input: esc tap "exit" -> transition: state.?
    state.?.conf.add_state -- input: an unoccupied key in the previous state (display: "[?] action trigger") -> set this key as the trigger input for the newly created state. then, transition: state.text_string[
            save = newly_created_state.name
            exit = (transition: state.?)
            cancel = (remove newly_created_state and its trigger from state.?. transition: state.?)
        ]
        the key can be any unoccupied key of state.?, including the key currently shown for configure/back/search (they then move, see state.?).

    state.?.conf -- "add a function"-> state.?.conf.add_func
    add_function is like adding transition to a state that calls a function on transition
    state.?.conf.add_func first asks what kind of function to add. like state.?.conf it has no user bindings, so its keys are the first available keys:
        choose resource to activate (script/app/open file)  ⌘
        choose builtin function                             R⌘
        exit                     ⎋
    state.?.conf.add_func -- input: esc tap "exit" -> transition: state.? (nothing created)
    state.?.conf.add_func -- input: ⌘ "choose resource to activate (script/app/open file)" -> state.?.conf.add_func.trigger[kind = resource]
    state.?.conf.add_func -- input: R⌘ "choose builtin function" -> state.?.conf.add_func.trigger[kind = builtin]

    state.?.conf.add_func.trigger -- input: esc tap "exit" -> transition: state.? (nothing created)
    state.?.conf.add_func.trigger -- input: an unoccupied key in state.? (display: "[?] function trigger") -> set this key as the input trigger for the newly created function. transition: state.text_string[
            save = newly_created_function.name
            exit = (kind resource: transition: state.file_select[
                        save = newly_created_function.target (the file)
                        exit = transition: state.?
                        cancel = (remove newly_created_function and its trigger from state.?. transition: state.?)
                    ]
                    kind builtin: transition: state.builtin_select[
                        save = newly_created_function.target (the builtin function)
                        exit = (if the chosen builtin takes an argument (see builtin toolkit): transition: state.text_string[
                                    save = newly_created_function.argument
                                    exit = transition: state.?
                                    cancel = (remove newly_created_function and its trigger from state.?. transition: state.?)
                                ]
                                otherwise: transition: state.?)
                        cancel = (remove newly_created_function and its trigger from state.?. transition: state.?)
                    ])
            cancel = (remove newly_created_function and its trigger from state.?. transition: state.?)
        ]
        same key rules as add_state.
        a function is only kept once it has a name (can be empty) and a target (plus its argument, for a builtin that takes one). cancelling at any step leaves nothing behind.
        a builtin's argument never changes the function's name: the name is only what the user typed.
        the two kinds look different on purpose: "choose resource to activate" uses the system (finder) file picker, "choose builtin function" browses the builtin toolkit inside the display, with the same look and navigation as regular states.

    state.?.conf -- "delete a function"-> state.?.conf.del_func
        state.?.conf.del_func -- input: esc tap "exit" -> transition: state.?
        display list of functions:
        state.?.conf.del_func -- input trigger of the chosen function -> delete function. transition: state.?

    state.?.conf -- "rename a function"-> state.?.conf.name_func
        state.?.conf.name_func -- input: esc tap "exit" -> transition: state.?
        display list of functions:
        state.?.conf.name_func -- input: input trigger of the chosen function -> transition: state.text_string[
                save = chosen_function.name
                exit = state.?
                cancel = state.?
            ]

    state.?.conf -- "set function trigger"-> state.?.conf.set_input_func
        state.?.conf.set_input_func -- input: esc tap "exit" -> transition: state.?
        display list of functions:
        state.?.conf.set_input_func -- input trigger of the chosen function -> state.?.conf.set_input_func.set_input
            state.?.conf.set_input_func.set_input -- input: esc tap "exit" -> transition: state.? (trigger unchanged)
            state.?.conf.set_input_func.set_input -- input: new trigger (an unoccupied key of state.?) -> set chosen function.trigger to new_trigger. transition: state.?
            state.?.conf.set_input_func.set_input -- input: an occupied key -> ignored, stay in set_input

    state.?.conf -- "update function" -> state.?.conf.update_func
        display the same function list used by delete/rename/set trigger. choose an existing function by its trigger (or stand-in key for a disconnected trigger). state transitions aren't selectable.
        after choosing the function, show the same resource/builtin kind selection as add a function. then ask for its name (pre-filled with its current name), then select a resource with the file picker or a builtin from the toolkit, followed by that builtin's argument if needed. both file and builtin functions can be changed to either kind.
        the existing trigger stays unchanged. only save the updated name and target together after all selection steps complete, then return to state.?. cancelling at any step (including capslock exit or cancelling the file picker) leaves the original function completely unchanged.

    in the function lists above, only functions are shown and selectable (not transitions to sub-states). builtin and file functions are treated the same: both can be deleted, renamed, updated and given a new trigger.
    a function is chosen by tapping its own trigger. a function whose trigger is not available (see key_list) is given a stand-in key for the list instead: the first key in the key list not used by state.? or by another stand-in. it is displayed as "[stand-in] {name} — on [trigger] (key not connected)". this is how such a function can still be deleted, renamed, updated, or moved to an available trigger with set function trigger.

state.search
    a spotlight / raycast style search over everything discrete can open.
    entered from state.root (see state.?). like state.text_string, it opens a text prompt that starts empty and is typed into like a normal text field (key down, repeat, shift for capitals, delete, left / right arrows move the cursor).
    as the user types, suggestions are shown below the prompt. an empty prompt shows no suggestions.
    suggestion kinds:
        function: any function anywhere in the graph (the user's own functions, including ones whose target is a builtin). displayed with the path of states it lives in.
        the builtin toolkit itself (its folders and builtin functions) is never suggested here: builtins are only reachable through functions the user added. searching the toolkit is done by state.builtin_select.search.
        state: any state in the graph (except the root). displayed with the path of states it lives in.
        app: any app in /Applications, /System/Applications, ~/Applications (and their direct sub-folders, e.g. Utilities).
        file: files and folders in the user's home folder, found with the system's spotlight index by name. apps are not repeated as files.
    matching is case-insensitive (and diacritic-insensitive), ranked best first:
        exact name, name starts with the text, a word of the name starts with the text, name contains the text, the text's letters appear in order in the name (e.g. "vsc" -> "Visual Studio Code"), then meaning: a name with a word close in meaning to a word of the text (e.g. "mail" -> "inbox"), using the system's on-device word embeddings. meaning matching is not used for files.
        ties are broken by kind (function, state, app, file), then shorter name, then alphabetical.
    at most userSettings.maxSearchResults suggestions are shown (default 8).
    each suggestion is indexed by its ranking: the nth suggestion is shown with, and opened by, the nth digit key (1, 2, ... 8). one key, one event: a digit key never types into the prompt, whatever modifiers are held, so digits cannot be searched for. digit keys are identified by their physical position like every other key (the digit row only; keypad digits type normally). there are 9 digit keys, so suggestions past the 9th have no key.

    state.search -- input: any symbol key (except digit keys) / delete / left / right arrow -> edit the text (as state.text_string), suggestions update, no state transition
    state.search -- input: digit key n -> open the nth suggestion. nothing happens if there is no nth suggestion.
    state.search -- input: esc -> discard the text. transition: the state search was opened from (state.root when opened with the root's search action, or the state holding the builtin search function that opened it). (displayed: "[⎋] exit")
    opening a suggestion:
        function -> run the function exactly as its own trigger would (see running a function). this works even when its trigger key is not connected. running a builtin search function from here clears the text and stays in state.search (esc still returns to where search was first opened).
        state -> transition: that state (its back action returns to its parent, as usual).
        app -> open the app, exit discrete.
        file -> open it with its default app (a script is opened, not run), exit discrete.
    other non-character keys (tab, enter, up / down arrows, f keys, ...) are ignored.

below is the abstraction of how editing text work (for arbitrary save, exit and cancel)
state.text_string [
    save
    exit
    cancel (defaults to exit if not given)
]
    typing in state.text_string works like a normal text field, not by the tap rule: keys act on key down, holding a key repeats it, and shift (and other modifiers) are used for typing, e.g. shift + a types "A".
    the text starts empty.
    the display shows the text with a visible cursor.
    state.text_string -- input: any symbol key -> insert the character at the cursor, no state transition
    state.text_string -- input: delete -> remove the character before the cursor, no state transition
    state.text_string -- input: left / right arrow -> move the cursor, no state transition
    state.text_string -- input: enter -> save text_string (can be empty) to the "save" destination. then, transition: "exit". (displayed: "[⏎] save")
    state.text_string -- input: esc -> discard text_string, "save" is not changed. transition: "cancel". (displayed: "[⎋] cancel")
    other non-character keys (tab, f keys, up/down arrows, ...) are ignored.

state.file_select [
    save
    exit
    cancel (defaults to exit if not given)
]
    opens the system file picker. discrete stops consuming keys while it is open so the picker can be used normally (capslock still leaves discrete).
    any file can be selected: an app is opened, an executable script is run, any other file is opened with its default app.
    state.file_select -- user select a file -> set "save" to the file. transition: "exit"
    state.file_select -- user cancels the picker -> "save" is not changed. transition: "cancel"

builtin toolkit
    the builtin toolkit is a tree shipped with discrete, built like the user's graph but fixed and read-only: the root folder (named "builtin functions") holds builtin functions and builtin folders, and a folder can hold more functions and folders. the user cannot add, delete, rename or rebind anything in it.
    each builtin has a stable id (what a function's builtin target stores), a name and an order inside its folder.
    a builtin may take an argument: text asked for (with state.text_string, under the builtin's prompt) right after the builtin is chosen, stored with the function, and used every time the function runs.
    the toolkit currently contains (builtins.txt lists the same for developers, with ids and source files):
        builtin functions (root folder)
            search -- opens state.search (the same search the root's search action opens). stays active (exception to the exit rule).
            move window to next monitor -- moves the focused window of the frontmost app to the next monitor, then exits.
                monitors are ordered left to right (then top to bottom), wrapping from the last back to the first.
                the window keeps its size (shrunk to fit if the next monitor is smaller) and its relative place on the screen (a window flush right stays flush right).
                a maximized window (one that fills its monitor's usable area, below the menu bar and beside the dock) is maximized again on the next monitor: it fills that monitor instead of keeping its size and place.
                a full-screen window can't be moved while in full screen, so it leaves full screen, moves to the next monitor (maximized), and goes full screen again there.
                with one monitor, or no focused window (e.g. no window open), nothing happens.
            open website -- argument: "website url or ip address". opens it in the default browser, which comes to the front, then exits.
                an address without a scheme gets one: http:// for an ip address or localhost, https:// otherwise (e.g. "github.com" -> https://github.com, "192.168.1.1:8080" -> http://192.168.1.1:8080).
                an empty or unusable address opens nothing (discrete still exits).
            trackpad functions (folder)
                toggle sketch mode -- turns sketch mode on if it is off, off if it is on, then exits.
                activate sketch mode -- turns sketch mode on (nothing changes if it is already on), then exits.
                deactivate sketch mode -- turns sketch mode off (nothing changes if it is already off), then exits.
            open application intelligently -- argument: "application name, bundle id, or .app path". uses intelligent application opening (above), then exits. examples: Visual Studio Code, com.microsoft.VSCode, /Applications/Visual Studio Code.app. an empty or unresolved argument opens nothing.
            toggle full-screen -- no argument. toggles native macOS fullscreen of the frontmost app's focused window, then exits. a normal window enters fullscreen; a fullscreen window leaves it. needs Accessibility permission. if there is no focused window or it doesn't support changing fullscreen, nothing happens (discrete still exits).
    sketch mode
        makes sketching on a laptop easier: while it is on, the trackpad works like a drawing tablet mapped onto the screen. it stays on until turned off (or discrete quits); it does not depend on discrete being active.
        only touches with a single finger change. while exactly one finger is on the trackpad:
            the pointer goes to the place on the screen that matches the finger's place on the trackpad: the trackpad's centre is the screen's centre, its top right corner is the screen's top right corner, and so on. the screen is the one the pointer is on when the finger touches down.
            the left mouse button is held down where the finger touched, and moving the finger drags (draws).
            lifting the finger releases the button. the pointer stays where it is.
            a quick tap clicks where the finger touched.
            the trackpad's own pointer movement and left clicks (including tap to click) are held back, so they don't fight the drawing.
        touches with two or more fingers work as usual (scrolling, two finger click, pinch, swipes, three finger drag, ...). if a second finger joins while one finger is drawing, the stroke ends (button released) and the touch is left alone until every finger has lifted.
            a lone finger only presses once it has stayed alone for a moment (about 60ms), so the first finger of a two finger gesture doesn't draw a dot.
        only fingertips count as fingers: parts of a resting hand that touch the trackpad (e.g. its side along the trackpad's edge) are ignored, like macOS's own palm rejection, so they never move the pointer, press, or end a stroke.
        a mouse works as usual while no finger is on the trackpad.
    unless its description says otherwise, a builtin function exits discrete after it runs, like a file target.
    if a function's builtin target no longer exists (a later version removed it), the function is kept, displayed dimmed and marked "(builtin not available)", and cannot be run. it can still be deleted, renamed or given a new trigger.

state.builtin_select [
    save
    exit
    cancel (defaults to exit if not given)
]
    browses the builtin toolkit to choose a builtin function. it looks and navigates like regular states (see display and state.?): the top line is the current folder's name, each row is "[key] name", and the capslock row is last. it is opened at the toolkit's root folder.
    keys are assigned automatically, since the user binds nothing here. in each folder, from the first key of the key list (except capslock and esc):
        root folder: "search builtin functions" (state.builtin_select.search), then the folder's entries in toolkit order.
        this search replaces regular search while selecting a builtin: here the user must pick a builtin function, so files, apps, states and the user's functions are never suggested.
        any other folder: "return to previous folder", then the folder's entries in toolkit order.
    so with the current toolkit the root shows: [⌘] search builtin functions, [R⌘] search (the builtin function), [⌥] move window to next monitor, [R⌥] open website, [⌃] trackpad functions, [R⌃] open application intelligently, [⇧] toggle full-screen, [⎋] cancel, [⇪] exit discrete.
        and the trackpad functions folder shows: [⌘] return to previous folder, [R⌘] toggle sketch mode, [⌥] activate sketch mode, [R⌥] deactivate sketch mode, [⎋] cancel, [⇪] exit discrete.
    there is no configure action: the toolkit cannot be edited.
    state.builtin_select -- input: key of a builtin folder -> show that folder, no save
    state.builtin_select -- input: "return to previous folder" -> show the parent folder
    state.builtin_select -- input: key of a builtin function (a leaf) -> set "save" to that builtin function. transition: "exit"
    state.builtin_select -- input: "search" (root only) -> state.builtin_select.search
    state.builtin_select -- input: esc -> nothing is chosen, "save" is not changed. transition: "cancel". (displayed: "[⎋] cancel")
    any other key is ignored.

state.builtin_select.search
    the same as state.search (same text prompt, matching, ranking, digit keys, display of paths), but the suggestions are only builtin functions and builtin folders from the builtin toolkit. kind ties are broken function first, then folder. folder and function suggestions are displayed with their path of folders.
    opening a suggestion:
        builtin function -> choose it, exactly as tapping its key in state.builtin_select: set "save" of state.builtin_select to it. transition: its "exit"
        builtin folder -> transition: state.builtin_select showing that folder (its "return to previous folder" goes to its parent folder, as usual)
    state.builtin_select.search -- input: esc -> discard the text. transition: state.builtin_select at the root folder (nothing chosen yet). (displayed: "[⎋] exit")
