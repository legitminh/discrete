i want to implement a productivity tool like this (on my mac). I want the tool to be available on start up. it listen to certain key combos and run script/action/open apps when the key is triggered. for the MVP, holding CapsLock open a menu of abilities (where CapsLock + C opens VSCode, CapsLock + M opens mail, etc, if Capslock released without any specification, its a regular capsloc). But there is more, I could enter a command mode using Capslock + series of keys that can run scripts, open browser page, or do anything automatically!
entry
    when i click capslock. the overlay show all options
    a default option is configure
display
    the top line should be the state's name
    each line after is an action of the state, sorted by their key's assignment
underlying mechanism
    the app manage a graph of nodes called states (how this is stored depends on implementation).
    here is the highest order state transition
        regular computer use -- action: press other keys, use mouse, ect -> regular computer use
        regular computer use -- action: tap capslock -> discrete command root/home state
    while the user is not using their computer regularly (discrete active), the discrete UI interface will be displayed (otherwise discrete runs on the background). while discrete active, here are some default mappings
        discrete.home -- action: tap delete -> settings
        discrete.home -- action: tap capslock -> exit discrete and return to regular computer use
        the UI will display all these actions as a list, the input's symbol and then the text description of what the input does to the state: for instance, "[delete symbol] settings" is the first row
    while the user is at a state (such as home), theses are actions they can take (again, will be displayed)
        (if there is a previous state) state -- action: system decide, 1st unoccupied key in key list -> return to previous state
        state.? -- action: 1st unoccupied key in key list "configure" -> state.?.conf
            state.?.conf -- action: system decide, 1st unoccupied key in key list "add state"-> state.?.conf.add_state
                state...add_state -- action: an unoccupied key in the previous state (the display of this action is "[?] create new action") -> set this key as the activation key for the newly created state accessible through action ? (the key specified by the user). after than, enter the rename state of the newly created state.
            state.?.conf -- action: system decide, 2nd unoccupied key in key list "add an action"-> state.?.add_action
                add action is like adding a state, but an action is a leaf node that does a scripted function.
                state...add_action -- action: an unoccupied key in the previous state (the display of this action is "[?] create new action") -> set this key as the activation key for the newly created action accessible through action ? (the key specified by the user). then, ask for action name. after that, open file system for user to select a script to run when this action is triggered.
            state.?.conf -- action: system decide, 3nd unoccupied key in key list "rename an action"-> state.?.rename_action
            state.?.conf -- action: system decide, 4nd unoccupied key in key list "set an action trigger"-> state.?.conf.set_trigger_action.
                list of actions:
                state.?.conf.set_trigger_action -- user click corresponding trigger key of the chosen action -> state.?.set_trigger_action.set_trigger.
                    state.?.set_trigger_action.set_trigger -- user click new trigger key for the action -> set the key and return to state.?
            state.?.conf -- action: system decide, 5th unoccupied key in key list "delete action"-> state.?.conf.set_trigger_action.
                list the actions:
                state.?.conf.set_trigger_action -- user click corresponding trigger key of the chosen action -> delete action and return to state.?
            state.?.conf -- action: 6th unoccupied key "delete this state" -> (this is only available for the non-root node). delete the state and transition to the state's parent.
            state.?.conf -- action: 7th unoccupied key "rename this state" -> rename the current state being configured, then transition to the state itself so the user can see the result of configuration.
        for as many user defined actions:
            state.? -- action: key the user defined "[key]{new state name}" -> go to state.?.next? if the action transitions to a new state or trigger the script if is leaf node
    the system should keep track of key list, a list of possible keys on the device (this can be hard coded fornow)
    all the actions can be set to anything (assuming no overlap). the key list is ordered, and that should be the display order of actions
